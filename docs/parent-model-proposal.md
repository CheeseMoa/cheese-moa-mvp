# 학부모 접근 모델 전환 — FE 제안 및 BE 협의 요청

> **협의용 제안 문서입니다(확정 아님).** 합의된 내용은 이후 `api-spec.md`에 반영합니다.
> 목표는 **계약(스키마·필드·의미) 합의**입니다 — 합의만 되면 FE는 MSW 목 선행으로 병렬 진행하고, 실연동 검증만 BE 배포를 기다립니다.

## 0. 배경

- 2026-07-17 법률 자문 결과, **학부모 무로그인 뷰어(링크+비밀번호)를 폐기**합니다. 다른 아이 사진 열람이 개인정보 **제3자 제공**에 해당해 동의가 필요한데, 무로그인 링크로는 동의 주체를 특정할 수 없기 때문입니다.
- 대안: **학부모도 로그인(소셜 로그인 그대로)하고, 모임에 멤버로 합류**합니다. 초대·합류 시점에 동의를 수집할 수 있게 됩니다.
- 미배포·사용자 0명이므로 **데이터 마이그레이션은 없습니다.**

## 1. 역할(role) 모델 — FE 제안

**계정 유형을 나누지 않습니다.** 전원 동일한 일반 유저(소셜 로그인 4종 그대로)이고, role은 **모임 멤버십 단위**(user × group)로 둡니다.

- role 값: `TEACHER` / `PARENT` (네이밍은 BE 결정 따름)
- **결정 방식: 초대 링크(joinKey) 2종** — 선생님용 / 학부모용. 어느 링크로 합류했는지가 그 모임에서의 role을 정합니다(수락 플로우에 역할 선택 화면 없음). 합류 후 role 변경·관리자 지정 개념은 도입하지 않습니다.
- **합류는 역할 무관 승인제** — 링크로 참여하면 곧바로 멤버가 되는 게 아니라 **신청(PENDING)** 상태가 되고, 기존 선생님이 승인해야 멤버로 확정됩니다. **선생님 role 신청도 동일하게 승인 대상**입니다. 승인은 역할 불문 **멤버 확정만** 하는 단순 액션이고(인물과 무관), 학부모의 인물 연결은 승인 후 **별도 액션**입니다(§2). 승인 전 신청자는 모임 콘텐츠에 접근할 수 없습니다.
- 같은 사람이 A모임에선 선생님, B모임에선 학부모일 수 있습니다(교사이면서 학부모인 케이스).
- FE `Group` 타입에 이미 `role` 필드 자리가 있습니다(현재 항상 null) — 모임 목록/상세 응답에 **내 role**을 채워 주시면 됩니다.

### 권한 매트릭스 (서버 강제 필수)

이번 전환이 법적 요구에서 출발했으므로, 학부모 차단은 FE 버튼 숨김이 아니라 **서버가 403으로 강제**해야 합니다. 에러 코드는 BE 결정 따름(FE는 코드 매핑만 추가).

| 액션 | TEACHER | PARENT |
|---|---|---|
| 사진 업로드·분류(분석) | O | X |
| 검토·공개(발행) | O | X |
| 모임·이벤트·앨범 설정/삭제/이름수정 | O | X |
| 합류 신청 승인·거절, 매핑(자녀 연결)·해제 | O | X |
| 초대 링크 발급·조회 | O | X (열린 질문 Q3) |
| 조회 | 전체 | 매핑된 인물 + 공통, published만 |
| 다운로드 | 전체 | 본인 노출 범위만 |

## 2. 열람 권한 — 인물(personId) 매핑 + 신청–승인

권한의 실체는 **학부모 계정 ↔ 인물(personId) 매핑, 모임 단위**입니다. 앨범 단위가 아니므로 **새 이벤트가 생겨도 재부여가 필요 없습니다**(인물은 모임 단위로 이벤트를 관통하므로).

### 매핑 생성 흐름: 신청 → 승인

1. 학부모가 학부모 링크로 합류할 때 **자녀 이름을 자유 텍스트로 입력**(신청). 다자녀는 복수 신청.
2. 선생님이 신청을 **승인**(멤버 확정) 또는 거절합니다 — 승인은 인물과 무관한 단순 액션입니다(`personId` 불필요).
3. **인물 연결은 승인 후 별도 액션**: 학부모 목록에서 [연결] → 인물 앨범을 골라 매핑을 생성합니다. 신청 때 적은 자녀 이름 텍스트는 **연결 전까지 보존**해 주세요(연결할 때 선생님이 참조).
4. **승인 전엔 아무것도 안 보이고, 연결 전엔 공통 사진만** 보입니다(Q1 확정).
   - 학부모 초대(학기 초)가 첫 사진 업로드(행사 후)보다 먼저인 게 보통이므로, "승인됐지만 미연결" 구간은 예외가 아니라 기본 경로입니다. 미연결은 별도 상태가 아니라 **매핑 0건인 PARENT 멤버**로 파생됩니다(스키마 추가 없음).

설계 근거 두 가지:

- **이름 일치 자동 매핑은 금지** — 아무 학부모나 남의 아이 이름을 입력하면 열람되는 구조는, 무로그인 뷰어를 폐기한 이유(제3자 제공)를 그대로 재현합니다. 매핑엔 반드시 선생님 승인이 들어가야 합니다.
- **신청 UI에 인물 목록을 노출하지 않습니다**(원아 명단 노출 방지) — 그래서 자유 텍스트 신청 + 선생님이 승인 시 인물 선택 구조입니다.

카디널리티: 한 학부모 ↔ 여러 인물(다자녀), 한 인물 ↔ 여러 학부모(부·모) 모두 허용.

### 필요 API (예시 — 경로·이름은 BE 결정)

| 용도 | 예시 |
|---|---|
| 합류 신청 생성 (역할 공통 — 학부모는 자녀 이름 포함) | `POST /groups/:id/join-requests` `{ role, childNames? }` |
| 대기 신청 목록 (선생님) | `GET /groups/:id/join-requests?status=PENDING` |
| 승인·거절 (역할 공통 — 인물과 무관) | `PATCH /join-requests/:id` `{ status }` |
| 멤버 목록 (role·매핑 여부·신청 자녀 이름 포함) | `GET /groups/:id/members` |
| 매핑 생성·해제 (선생님 — 승인 후 별도 액션) | `POST` / `DELETE /groups/:id/person-parents` `{ userId, personId }` |

## 3. 학부모 조회 플로우·API — 목록은 재사용, 사진 조회는 전용 엔드포인트

학부모 화면 플로우는 **모임 → 이벤트 → 사진(플랫)** 입니다. 앨범 계층이 없습니다(자녀 1~2명이라 앨범 층이 무의미).

### 재사용 (기존 엔드포인트 + role 반영)

- `GET /groups` 목록·상세: 학부모도 멤버이므로 그대로 동작. 응답에 **내 role** 추가만.
- 이벤트 목록: 학부모에겐 **공개(published)된 이벤트만 서버 필터**.

### 신설 (학부모 전용 사진 조회)

- 예: `GET /events/:id/parent-photos` — 이 이벤트에서 **이 학부모가 볼 수 있는 사진 전체를 플랫하게** 반환.
  - 범위: 매핑된 인물의 사진 + 공통(단체) 사진(Q1 확정 — 특수 앨범은 은닉), **published만**.
  - 검토 상태·발행 대기 수 등 제작자용 필드는 응답에서 제외.
- 다운로드: 같은 범위의 **이벤트 단위 zip** 1개 (예: `GET /events/:id/parent-photos/download`).

### 전용 엔드포인트를 제안하는 이유

1. **화면 하나 = 호출 하나** — 제작자용 앨범 API 재사용이면 FE가 앨범 목록 → 앨범별 사진 N회 호출 → 병합해야 합니다.
2. **노출 필터 실수가 곧 법적 사고인 도메인** — 제작자 엔드포인트에 role 분기를 끼워 넣으면 분기 하나 누락이 유출 경로가 됩니다. 전용 엔드포인트는 기본 차단(deny) + 명시적 허용 구조라 안전 방향이 반대입니다.
3. **기존 뷰어 로직 이관으로 충분** — 현행 뷰어 엔드포인트가 이미 published 사진 서버 필터링(CHMO-324)을 갖고 있습니다. 인증을 viewerToken → accessToken+멤버십으로 바꾸고 인물 매핑 조건을 추가하는 **개명·이관**에 가깝습니다.

### 공개(publish) 모델은 유지 — FE 제안

검토/발행 분리·재공개 게이트(CHMO-324·265)는 그대로 두고, **노출 조건의 "뷰어 토큰" 자리만 "PARENT 멤버십 + 인물 매핑"으로 대체**합니다: 학부모 노출 = `published && (매핑된 인물 || 공통)`. 최근 배포하신 발행 로직을 버리지 않는 최소 변경안입니다.

## 5. 동의 수집 — 자녀 정보 처리 동의 1건 확정, 제3자 제공은 추후 협의

- **확정(BE CHMO-586·FE CHMO-587)**: 학부모 합류 신청(3/3)에서 **자녀의 사진·얼굴 특징정보 처리 동의**를 수집한다 — 동의권자(보호자) 본인이 남기는 기록이라 선생님의 확인(`CHILD_CONSENT_ATTESTED`)과 증빙력의 급이 다르다. 신청 body `childConsentVersion`으로 버전을 동봉하고 BE가 `UserAgreement`(모임 단위) 행으로 저장한다(신청 시 기록·append-only·멱등 — 계약은 `parent-model-api-draft.md` §3·§8).
- **제3자 제공 동의는 법률 확인 후 후속 협의** — 공통 사진(여러 아이 동반) 노출이 제3자 제공에 해당하는지 미확정(`app-copy.md` §7 `[[검토필요]]`). 확정되면 같은 자리(합류 신청)에 항목을 더한다.

## 7. 후속 협의 — BE 추가 질문 3건에 대한 FE 안 (2026-07-25)

**7-1. 재분석으로 인물이 병합·소멸하면 그 인물의 매핑은? — 2단 방어 (2026-07-25 확정)**

**1차 — 예방 (AI 파이프라인 규칙 요청): 매핑된 인물은 보호 대상.**
- 병합 시 한쪽에만 매핑이 있으면 **매핑된 인물을 남기고 그쪽으로 흡수** — 연결이 끊길 상황 자체를 제거합니다.
- **양쪽이 서로 다른 학부모에 매핑돼 있으면 자동 병합 보류** — 기계가 판단하면 안 되는 케이스라 선생님 개입으로 넘깁니다.
- 매핑된 인물의 자동 삭제 금지.

**2차 — 안전망 (그래도 소멸하는 경우): 자동 해제 → 미연결 회귀. 자동 재매핑 금지.**
소멸은 AI만이 아니라 **선생님의 정상 행동**으로도 일어납니다(사진 전량 삭제·이동 → 빈 앨범 자동 삭제(CHMO-231), 이벤트 삭제) — 그래서 예방만으로는 부족하고 안전망이 필요합니다. 이때 어떤 **자동 승계·자동 재매핑도 하지 않고** 매핑을 해제해 기존 "미연결"(매핑 0건)로 되돌립니다. 잘못 승계되면 다른 아이 사진이 열리는, 정확히 이 전환이 막으려는 사고이기 때문입니다. "재승인 대기" 같은 **새 상태는 만들지 않습니다**(합류 승인은 유효, 매핑만 풀린 것) — 신청 자녀 이름이 보존돼 있으니 선생님은 초대 관리의 기존 [연결] 흐름으로 재연결합니다.

**7-2. PENDING 학부모의 화면 상태를 어디에 실을지 (2026-07-25 확정)**
"모임 상세에 싣자"는 안엔 **반대** — PENDING에게 상세 API를 여는 순간 기본 차단(deny-by-default) 원칙이 깨집니다(상세엔 이벤트 목록 등이 실림). 대신 **모임 목록(GET /groups) 항목에 `myMembership: { role, status, claimedChildNames }`**를 실어 주세요. 상세 API는 ACTIVE 멤버 전용을 유지합니다.

화면 처리(확정): **대기 전용 화면을 두지 않습니다.** 홈 카드에 "승인 대기중" 배지를 달고 카드를 **비활성(탭 불가)**으로 둡니다 — 탭하면 토스트("선생님 승인을 기다리고 있어요")만. 신청 완료(3/3 동의) 후 랜딩도 홈이며, 비활성 카드 자체가 "신청됨" 피드백입니다. 카드에 `claimedChildNames`로 "신청: 김민준"을 표기해 학부모가 자기 신청 내용을 확인할 수 있게 합니다. **PENDING 사용자는 모임 관련 API를 아예 호출하지 않습니다** — 목록 응답 하나로 끝.

**7-3. 모임 상세 멤버 수·목록에 학부모 포함? (2026-07-25 확정)**
포함하되 **합산 금지** — `memberCount` 하나로 합치면 선생님에게 의미가 없어집니다. **`teacherCount` / `parentCount` 분리**를 요청합니다(05 헤더 표기: "선생님 3 · 학부모 12 · 이벤트 8"). 멤버 목록도 role 구분 포함(초대 관리 화면의 데이터 소스). 반대 방향 주의: **학부모(PARENT) 화면에는 멤버 정보를 일절 내리지 말아 주세요** — 다른 학부모 명단·원아 이름이 학부모에게 보이는 것 자체가 개인정보 노출입니다.
